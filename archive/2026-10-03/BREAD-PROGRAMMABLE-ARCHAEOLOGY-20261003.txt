BREAD PROGRAMMABLE-WORLD / PRODUCT ARCHAEOLOGY — 2026-10-03
Owner: bread_programmable_archaeology (Codex), read-only scout.

Recommendation in one paragraph
Bread's strongest near-term contribution is a set of coherent activities: people compose a source-linked notebook, define a reusable object/tool from its own editable source, delegate bounded work to a resident, and inspect the resulting source, changes, refusals and history through the same object. An inspector connects those activities; it is not the entire product. Bread also contains collaborative document offerings, a review/forge model, a captured world atlas, and attributed creator/remix commons. Mini should take the experience and several pure leaf representations, while preserving its own signed authorized projections, source-owned semantics, protected fragments, exact resident request identity and operation recovery. Importing Bread's desktop World/ledger, public demonstration identity, heap writers or proof-gated trust wholesale would regress those properties.

1. A shared source-linked notebook: compose evidence, discuss it, assign work, preserve exact citations
Human scenario: a community maintains a project notebook or collective research plan. One member embeds an independently owned section, quotes a pinned past source, annotates a precise range, and asks a resident to explain or review it. Another member can edit only their authorized part. A refused save retains the draft; an unreadable child remains a labelled darkened reference. The notebook presents authored text, source ancestry, comments, selected object view and resident status as one experience.

Bread maturity: dregg-doc is substantial real patch algebra, explicit conflicts, provenance, source syntax and composition prototypes. doc.rs computes Add/Delete/Connect patches from token LCS. literate.rs roundtrips visible conflict blocks; resolution.rs supplies keep/order/field resolution. composition.rs supplies a separate LayoutGraph, full-width child CellId, live versus pinned references, Section/Figure/Inline/Block/Citation roles, independently edited layout and children, bounded darkening/cycle behavior. This is a pure separate prototype rather than a widened production Atom. document_composer.rs is an actual consumer, but its returned Receipt is an Author/PatchId tuple, not a kernel receipt. marks.rs is a separate pure monotone overlay with stable atom endpoints and tombstones; lib.rs explicitly says marks are not yet projected into the substrate.

Actual collaborative offering: dreggnet-doc/src/lib.rs consumes MultiEditorDoc and renders ViewNode. MultiEditorDoc (dregg-doc/src/executor_drive.rs:457,604) owns one ledger with multiple editor agents, plans before commit, mutates the witness graph only after a committed TurnExecutor result, and preserves per-agent nonce/receipt chains across interleaving. The offering defaults to refusal of unresolved conflict, with a carrying_prose_conflicts option and explicit alternatives. This is stronger evidence than a static DocGraph toy; it is still a single sequenced executor, not concurrent replicas.

Critical liabilities: desktop edit_doc (starbridge-v2/src/deos_desktop/mod.rs:2989) first mutates local history, then commit_doc_to_umem_heap writes through World::set_cell_heap out of band, then saves sidecar, then tries the revision turn. A refused turn can leave changed heap. commit_set_field also writes LE bytes in the low eight bytes, incompatible with the canonical BE/last-eight convention used elsewhere. The heap readback/reopen test is explicitly not an authorized edit proof. dreggnet-doc's current-roster rebuild recreates the document and DROPS previously landed edits that cannot replay after an editor is downgraded to commenter (lib.rs around340). Revocation thereby rewrites the past. Its public constant RECEIPT_SIGNING_SEED=[0x5c;32] and deterministic editor seeds are demo identities; the 'non-fabricable' description is not an adversarial credential guarantee. Doc::text omits conflict alternatives, and full-text editing repeatedly replays history and uses a quadratic token-LCS table. Receipt/pin widths in some pure prototypes are u128, not Mini's security identity.

Mini consumer: M/native/resource-client/src/protected_annotations.rs already binds sealed comment bodies to annotation ID, atom and revision; source range publication/live transclusion is in workspace.rs around1547; separately authorized source/history projections at1698-1957; render/history.rs shows actual authorized historical source or not-covered state. web.rs exposes editor, historical/source links.
