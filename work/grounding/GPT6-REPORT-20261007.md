### A1. Active-frame view stability

**Asked.** Prove what the re-entry guard actually buys: `frameReturn` applies edits to the current state, so the property is that no descendant can change the frame's own object between entry and return (`before = viewed`), not merely that the stack is `Nodup`. Keep an explicit DAO witness as a test.

**Built** (commit `8aa18463`, theorems only; nothing new refuses; no re-genesis).

[`Kernel/ObjectiveCall.lean#L2420`](https://github.com/emberian/minidregg/blob/061fcfc1feb476ab5775ad85743e9a3eec0f265a/Kernel/ObjectiveCall.lean#L2420):

```lean
theorem active_frame_view_stability {rootBytes : Bytes → Digest} (config : Config) (snapshot : Snapshot rootBytes)
    (height : Nat) (authority : Authority) (turn : TransactionId) {fuel : Nat} {stack : List Ctx} {call : CallPlan}
    {journal journal' : Journal} {ticks left : Nat} {result : Data}
    (ran : exec config snapshot height authority turn fuel stack (.enter call) journal ticks = .ok (result, journal', left))
    (distinct : (stack.map (·.object)).Nodup) (read : ObjectsRead config snapshot journal) :
    (∀ ctx ∈ stack, journal'.lookup ctx.object = journal.lookup ctx.object) ∧
    ∃ new, journal'.writes = journal.writes ++ new ∧ ∀ w ∈ new, w.before = w.viewed
```

The first conjunct is the stability property: a subtree entered from any stack of distinct objects leaves each stacked object's state unchanged in the journal. The second says every write the subtree appends was applied to exactly the state its frame was shown. The invocation-level corollary is [`invocation_writes_from_view` (#L2401)](https://github.com/emberian/minidregg/blob/061fcfc1feb476ab5775ad85743e9a3eec0f265a/Kernel/ObjectiveCall.lean#L2401):

```lean
theorem invocation_writes_from_view {rootBytes : Bytes → Digest} {config : Config} {snapshot : Snapshot rootBytes}
    {height : Nat} {request : InvokeRequest} (invoked : Invocation config snapshot height request) :
    ∀ w ∈ invoked.journal.writes, w.before = w.viewed ∧
      w.record.judge w.facts (some w.before.value) w.after.value = .ok ()
```

For a delivered message's call tree, `runMessage_writes_from_view` ([`Kernel/ObjectiveSend.lean#L572`](https://github.com/emberian/minidregg/blob/061fcfc1feb476ab5775ad85743e9a3eec0f265a/Kernel/ObjectiveSend.lean#L572)) gives the same.

### A2. Grants v2: delegation bound to code, arguments and caller

**Asked.** Grants bind (target, method, interface/code id, canonical args, scope, uses), with an optional caller or tree-position restriction. Use bounded constraints (recipient, cumulative cap) instead of widening. Prove "every frame receiving delegated authority has a matching unconsumed authorization". Keep delegation (request/subject) separate from consent (law).

**Built** (commits `0d53ced0` kernel, `8036c76d` theorem, `652a6828` journey, `0f3fce22` doc and lemma).

The grant shape is in [`Kernel/ObjectiveCall.lean#L482`](https://github.com/emberian/minidregg/blob/061fcfc1feb476ab5775ad85743e9a3eec0f265a/Kernel/ObjectiveCall.lean#L482) and [#L514](https://github.com/emberian/minidregg/blob/061fcfc1feb476ab5775ad85743e9a3eec0f265a/Kernel/ObjectiveCall.lean#L514):

```lean
inductive ArgsBound where
  | exact (digest : Digest)
  | recipient (path : List String) (value : List UInt8) (cap : Option (List String × Nat))
  | capped (path : List String) (limit : Nat)

structure Grant where
  object : Nat
  method : String
  code : Digest
  args : ArgsBound
  caller : Option Nat
  uses : Nat
```

- `code` is the package the target must run (its `activePin`).
- `exact` is a tagged cSHAKE256 digest ("DREGG/OBJECTIVE/CALL/GRANT-ARGS/v1") over the canonical `dataBytes` of the arguments.
- There is no wildcard constructor.
- `Journal.grants` is the signed list and never changes. Uses are recorded in `Journal.delegations`, one `Delegation` per delegated frame.

The authorization invariant is [`Authorized` (#L603)](https://github.com/emberian/minidregg/blob/061fcfc1feb476ab5775ad85743e9a3eec0f265a/Kernel/ObjectiveCall.lean#L603):

```lean
def Authorized (grants : List Grant) (delegations : List Delegation) : Prop :=
  (∀ d ∈ delegations, ∃ grant, grants[d.grant]? = some grant ∧ grant.Authorizes d) ∧
    ∀ index grant, grants[index]? = some grant →
      (usesOf delegations index).length ≤ grant.uses ∧
      ∀ path limit, grant.args.cap = some (path, limit) → chargedOf delegations index ≤ limit
```

The main theorem is [`invocation_delegated_authority` (#L2871)](https://github.com/emberian/minidregg/blob/061fcfc1feb476ab5775ad85743e9a3eec0f265a/Kernel/ObjectiveCall.lean#L2871):

```lean
theorem invocation_delegated_authority {rootBytes : Bytes → Digest} {config : Config} {snapshot : Snapshot rootBytes}
    {height : Nat} {request : InvokeRequest} (invoked : Invocation config snapshot height request) :
    Authorized request.grants invoked.journal.delegations ∧
      ∀ w ∈ invoked.journal.writes,
        (w.facts.subject = some request.subject ∧ w.facts.caller = none) ∨ w.facts.subject = none ∨
          ∃ d, w.delegation = some d ∧ d ∈ invoked.journal.delegations ∧ d.object = w.object.value ∧
            d.method = w.method ∧ d.code = w.record.activePin ∧ d.args = w.args ∧ d.caller = w.facts.caller
```

It rests on `exec_delegations` (#L2715, an induction beside `exec_invariant`) and on [`frameAuthority_spec` (#L2630)](https://github.com/emberian/minidregg/blob/061fcfc1feb476ab5775ad85743e9a3eec0f265a/Kernel/ObjectiveCall.lean#L2630), which says each frame's subject is the root's, none, or a spent grant.

### A3. Registered, authoritative invariant domains

**Asked.** Relational invariants as registered, authoritative invariant domains, checked in conjunction with per-frame laws, over bounded authenticated data, with no discovery calls.

**Built** in three ranges: range 1, range 2 steps 1 and 2, and range 3 (pricing). Design and as-built decisions are in `work/A3-INVARIANT-DOMAINS-DESIGN.md`.

*Range 1* (`9fdfdc1d` record, `487b54fb` judgment):
- New module `Kernel/ObjectiveDomain.lean`.
- A `Domain {members, law, payer}` lives in a protected activity-cell role `domain` (tag 6). Its id is a content address over members and law.
- `ObjectRecord.domains : List Digest` is the membership index.
- A new turn, `registerDomain`, takes 1..16 distinct members (at most 8 domains per object). The signer must hold a capability on every member. Each member consents under its upgrade policy: `memberFrozen` for a frozen member, `memberDenied` when a governed authority does not admit it, `memberDomainsFull` at the cap. The law must hold on the members' current states (`domainLawDenied` otherwise), and `domainExists` refuses a duplicate.
- At the end of every turn, `ActivitySeatEnd.finish` runs the seat join and then `judgeDomains` on the final posts. The domain only adds refusals.

[`judgeDomains_sound` (`Kernel/ObjectiveDomain.lean#L543`)](https://github.com/emberian/minidregg/blob/061fcfc1feb476ab5775ad85743e9a3eec0f265a/Kernel/ObjectiveDomain.lean#L543):

```lean
theorem judgeDomains_sound {rootBytes : Bytes → Digest} {config : Config} {snapshot : Snapshot rootBytes}
    {posts : List Post} {guards : List ReadGuard} {units : Nat}
    (judged : judgeDomains config snapshot posts = .ok (guards, units)) :
    ∀ object ∈ writtenObjects snapshot posts,
      guardAt snapshot (objectCell config.domain object) ∈ guards ∧
      ∀ record, finalRecord config snapshot posts object = .ok (some record) →
        ∀ id ∈ record.domains, ∃ domain states, finalDomain config snapshot posts id = .ok (some domain) ∧
          domain.members.mapM (finalState config snapshot posts) = .ok states ∧
          (∃ joint, jointSlots 0 states = some joint ∧ Minidregg.Pred.eval domain.law ⟨joint⟩ ⟨joint⟩ = true) ∧
          guardAt snapshot (domainCell config.domain id) ∈ guards ∧
          ∀ member ∈ domain.members, guardAt snapshot (stateCell config.domain member) ∈ guards
```

[`finish_domains` (`Kernel/ActivitySeatEnd.lean#L344`)](https://github.com/emberian/minidregg/blob/061fcfc1feb476ab5775ad85743e9a3eec0f265a/Kernel/ActivitySeatEnd.lean#L344) lifts this to the committed intent: every cell the judgment read is `Guarded` in `finalIntent` for every turn kind. So a concurrent write to an unwritten member conflicts instead of slipping past.

**A defect found while building range 1.** Before `487b54fb`, `AdmittedTurn.finalIntent` used a wildcard fallthrough (`| turn => turn.intent sealing`). It dropped `posts`/`extra` for every turn kind except birth, deliver, abandon, abortDrained and rebirth, so extra read guards added at turn end never reached the committed intent for create, invoke, deliverMessage, adopt, migrate, publish, resolve, topUp or exhaust. The fix lists every constructor, with no wildcard. The Lean plant `invoke-drops-guards` turns `finalIntent_guards` and `finish_domains` red.

*Range 2, step 1* (`c9c78525`): a new `Pred` atom `sumEq`. [`eval_sumEq` (`Pred/Core.lean#L530`)](https://github.com/emberian/minidregg/blob/061fcfc1feb476ab5775ad85743e9a3eec0f265a/Pred/Core.lean#L530):

```lean
theorem eval_sumEq (left right : List Slot) (old new : State) :
    eval (.sumEq left right) old new = true ↔
      ∃ xs ys : List Int, left.mapM new.get = some xs ∧ right.mapM new.get = some ys ∧
        xs.sum = ys.sum
```

How `sumEq` is classified:
- It is outside the decided `Pred.Sat` fragment, so floor decisions fail closed on it.
- On the coordination dial it is `.ordering`, with the reason proved as `sumEq_not_merge_closed` ([`Pred/CoordinationDial.lean#L419`](https://github.com/emberian/minidregg/blob/061fcfc1feb476ab5775ad85743e9a3eec0f265a/Pred/CoordinationDial.lean#L419)): 3+5 and 5+3 both back 8, but their slot-wise join 5+5 does not.
- The circuit compiler refuses it under every profile (`lower_sumEq_refuses`, [`Compiler/PredCompile.lean#L1558`](https://github.com/emberian/minidregg/blob/061fcfc1feb476ab5775ad85743e9a3eec0f265a/Compiler/PredCompile.lean#L1558)).

Policy-record token 17 = `sumEq`. No existing byte string changes meaning, so the policy frame stays v6.

*Range 2, step 2* (`ec312619`): the whole-history theorem. The design changed from a per-turn classification to one choke point at turn end. `judgeDomains` now:
- counts a retired or blanked state cell as a write of that member (before, only posts that carried a state payload counted);
- refuses `domainsDropped object` when a post rewrites an object record without every domain the held record names;
- judges and indexes every domain whose cell a post touches, refusing `domainUnindexed domain member` when a member's final record does not name it.

**Decisions and reasons.**

  - Transition rules stay the members' own per-frame laws.
  - Consequence: a domain law written with `monotone`/`writeOnce` is judged on new-vs-new and is therefore vacuous for those atoms. Nothing refuses such a law at registration (inferred from reading `judgeJoint`; not tested).

- *One choke point, not a per-turn list.* There are seven state-writing turns, and per-turn hooks would be seven places to forget. The choke point also makes the theorem independent of the `AdmittedTurn` constructor list.
- *Stale plans and concurrent commits are separated.* The native Host re-decides at submit (D3). Read guards protect a truly concurrent commit.
- *Pricing:*

The in-tree client tariffs (`activity_world.py`, `objective-native-acceptance.py`) set `domainWork: '0'`. So on default worlds the units are bounded by the declaration and the policy maximum (256), but cost nothing. Only the domain journey's world sets the rate to 1.
- *Membership is permanent* in these ranges. That is safe because it only refuses more.

## Row B — Activity semantics: the machine against a reference interaction tree

Permalinks below are to main `061fcfc1`.

### Asked

Relate a machine yield to a reference interaction `Vis(p, k)`: for every admissible response `r`, resuming the stored state corresponds to `k r`. Lift that through the call, send and await handlers. Distinguish silent divergence from eventual visible progress. Acceptance probe first: store a `Nat -> Activity<P,R,A>` factory, invoke it twice, and see two interactions.

### Built

**1. A reference interaction tree** (`Theory/ObjectiveBendInteraction.lean`, commit `19680933`). The reference is the program's own Core4 demand machine, run with no checkpointing and with resources only as large as needed. A node is one of `vis`, `ret`, `blackhole`, `refused`, `malformed` or `spin`. `spin` is silent divergence and has its own constructor ([P/Theory/ObjectiveBendInteraction.lean#L62](https://github.com/emberian/minidregg/blob/061fcfc1feb476ab5775ad85743e9a3eec0f265a/Theory/ObjectiveBendInteraction.lean#L62)):

```lean
inductive Node where
  | vis (plan : Data)
  | ret (result : Data)
  | blackhole
  | refused (reason : Refusal)
  /-- The program halted, but no resources make its Plan or result Data within the sizes. -/
  | malformed
  /-- Silent divergence: the program never halts. -/
  | spin

noncomputable def observe (b : Budget) : State → List Term → Node
```

`node_spin_iff` (L110) states `node b s = .spin ↔ ∀ n, ¬ Halts s n`. The yield theorem is at [L151](https://github.com/emberian/minidregg/blob/061fcfc1feb476ab5775ad85743e9a3eec0f265a/Theory/ObjectiveBendInteraction.lean#L151):

```lean
theorem node_of_chain_vis {s t : State} (h : Chain s t) {L' : Limits} {T' : Nat} {b : Budget} {d : Data}
    {y' : State} (ran : endsWith L' T' b t = some (.yielded d, y')) (valid : AddrValid y') {r' : Result}
    (found : ObjectiveBendDemandData.yieldedPlan L' b y' = .ok r') :
    node b s = .vis d ∧ ∀ (response : Term) (stored : State),
      resume response (checkpoint r'.state) = some stored →
      ∃ next, continuation b s response = some next ∧ Chain next stored

theorem chain_spin {s t : State} (h : Chain s t) {b : Budget} (spin : node b s = .spin) (L : Limits) (T : Nat)
    (b' : Budget) : endsWith L T b' t = none
```

"Every admissible response" means every response the kernel's `resume` accepts. `Chain` relates a lazy state to a normalized one by composed forcing, settling and collection steps (see Row C).

### Decisions

- **The reference is the program's own lazy machine, not a separate denotation.** This is the strongest reference we can state today. `docs/OBJECTIVE-BEND.md` ("What is open", Surface semantics) says that `.obend` has no meaning of its own (LT3). So "the activity is its reference interaction tree" means the kernel's checkpointed, metered execution equals the unmetered, uncheckpointed Core4 run of the same front-end output. It does not mean the kernel matches what the source says.
- **Faults are classified, not lifted.** A segment the handler turned into `faulted` is outside `History.reference`'s conclusion (`o.ran` is false). `delivery_refusal_reference` says what such a fault is, one delivery at a time. Its cases are the envelope running out, a `malformed` reference node (except for `suspended`), or a Plan the kernel does not perform.
- **`suspended` is a resource failure, not a semantic one.** It is the one extraction failure that does not transfer backward, and it is named and witnessed.

### Not done

- **Handlers not covered.** Activities that yield `call` or `send`, and an activity awaiting a message reply (`messageAwaitNeedsInbox`), are not built. The lift therefore covers activity await, call frames and message deliveries, but not await-on-message (doc "Not built"; cv `01a10ae9-7a1a`, open).
- **`History` is per record.** It does not fold `delivery_refusal_reference` into one statement over the whole history, and nothing composes histories across objects.
- **Divergence versus eventual progress.** `spin` is distinguished as a node, but nothing guarantees that a well-typed resident's segment terminates (doc "Guardedness (LT6)" open).
- **The factory probe is not a standing gate row** (read). It lives in `check-preview` inside `scripts/check-objective-frontend.sh`. That script is invoked from `scripts/local-gates.sh` and `.github/workflows/build.yml`, but not from the build-box merge gate (`scripts/pipeline/merge-gate-checks.sh`) or the journey runner. I did not verify that the GitHub workflow is enabled.
- **"Stored" is narrower than asked.** The factory is held in a `let`, def, record field or argument within one program run. It is not persisted object state invoked across turns.

## Row C — Checkpoint resources: semantic correspondence, quantitative refinement, deployed accounting

### Asked

Three obligations:
1. Semantic correspondence: the checkpoint invents no behaviour.
2. Quantitative refinement over a budget vector (ticks, heap, stack, materialization, sizes), in the converse direction: `N(s)⇓_B o ⇒ ∃B'. s⇓_{B'} o' ∧ o≈o'`. Relate continuation states, not only the next Plans.
3. Deployed accounting: the kernel admits and pays exactly what the refinement allows.

Also: don't make forcing free, and keep a deterministic byte representation for checkpoints separate from semantic heap equivalence.

### Built

**C1. The converse: "the difference is resources only"** (commit `19680933`; `Theory/ObjectiveBendDemandForcingBack.lean`, `...Converse.lean`, `Kernel/ObjectiveResumeContract.lean`). The proof is a backward simulation.
- `BackSim` ([Back L153](https://github.com/emberian/minidregg/blob/061fcfc1feb476ab5775ad85743e9a3eec0f265a/Theory/ObjectiveBendDemandForcingBack.lean#L153)) states that a forced run that halts has a lazy run that halts, ending related. The lazy run redoes the closed demands that the extraction cached; `pend_halts_back` shows they finish, with no halting premise.
- `Chain` ([Converse L153](https://github.com/emberian/minidregg/blob/061fcfc1feb476ab5775ad85743e9a3eec0f265a/Theory/ObjectiveBendDemandForcingConverse.lean#L153)) composes forcing, settling and collection steps.
- `Chain.back` (L163): whatever the normalized state ends with, the lazy state ends with the same ending above a threshold.

**C3. Deployed accounting** (commit `4aa9ddc5`, FLAG DAY).

The defect: every birth, delivery, exhaustion, seat method and call-frame extraction could spend up to `planBudget.ticks` forcing Plans and results. - `Capacity.extractTicks` is a 19th lane, with `Tariff.extractTicks` (tariff edition 2; an edition-1 tariff is refused).

```lean
structure SpendDeclared (config : Config) (resumed : State) (envelope : Capacity) : Prop where
  heap : (segmentLimits config resumed).heap ≤ envelope.heap
  stack : (segmentLimits config resumed).stack ≤ envelope.stack
```

### Decisions

**Extraction is checked against the declared allowance at actual spend, not by reserving the per-extraction maximum.** Three readings were on the table:
- Reserve the per-extraction ceiling at each extraction, as C3 first landed. This refuses honest trees: a yield-plus-return frame needs twice the ceiling.
- The OB-ENG deputy's fallback: reserve with a cap of `maxFrames × budget`. It withdrew this because it overcharges.
- Debit actual spend from a declared cumulative allowance. This was ruled by the root on 10-07 and approved by OB-ENG.

We chose the third for these reasons:
- The spend is deterministic (`planBudget.ticks - remaining.ticks`), so re-execution reproduces it exactly and admission stays a function of the request.
- An allowance covering the true sum always admits (`Journal.draw_two`).
- A shortfall is refused by name with the number that was short (`Journal.draw_short`).

The costs, stated plainly (from source reading; the last point is inferred from commit `6376fed8`'s message):
- **The fee is not the measured spend.** What the turn pays is the tariff price of the *declared* allowance. Unused allowance is not refunded (`refund_measurement_free`; the doc says "no fee depends on measured work"). "Actual spend" governs only whether the allowance suffices. A client that cannot predict its spend declares the published per-turn ceiling and pays for all of it. The test worlds author that ceiling as 16× the per-extraction maximum ([activity_world.py L81](https://github.com/emberian/minidregg/blob/061fcfc1feb476ab5775ad85743e9a3eec0f265a/native/resource-client/activity_world.py#L81)). That multiplier is an authored constant, not measured from the drivers' real usage.
- **Work happens before the debit.** An extraction runs to completion, up to the per-extraction ceiling, before its spend is drawn. A tree can do at most one per-extraction ceiling of forcing beyond its declared allowance before it is refused. Since row E (`6376fed8`), every call-tree refusal after the gate and signature is a charged failure: the payer pays the declared envelope's price. That overshoot is therefore paid at the declared price, not at its own measure. Before `6376fed8` it was unpaid.
- **Two shapes coexist.** Call trees draw actual spend. Birth, deliver, exhaust, ADOPT and `abortDrained` still require the full per-extraction ceiling up front: `planBudget.ticks ≤ envelope.extractTicks` ([L2364-2377](https://github.com/emberian/minidregg/blob/061fcfc1feb476ab5775ad85743e9a3eec0f265a/Kernel/ObjectiveActivity.lean#L2364)). The stated reason is that each performs exactly one extraction, and a budget failure there is committed as a program fault, so its budget must be the deployment's and not the client's. For those turn kinds this is a reservation of the maximum.
- **The pole is arithmetic.** `ceiling_reservation_refuses` is a lemma about `Journal.draw` applied twice to the ceiling. It is not a theorem about `exec` with reservation re-enabled. The executed red on call/send journeys at a4db78a7 is the behavioural pole.

**The converse threshold is existential, by design.** The converse is stated exactly as GPT-6 wrote it: ∃ a threshold vector, ∀ vectors above it. It is not "same budget, same result", which is refuted by `stored_commits_where_lazy_exhausts` and `stored_commits_where_lazy_extraction_fails`. The stored checkpoint saves work, so the lazy run legitimately needs more.

**Output sizes are not resources.** `withResources` varies heap, stack, ticks and extraction ticks, never the output node/byte budget. A `budget` extraction failure transfers backward unchanged (`Chain.failsBack`) because it is a property of the Data.

**Fixed-width spelling only where bytes are charged.** The deposit fix spells digests at 32 octets in the charged record only. It does not bound `Digest` itself. Bounding it would falsify Theory models whose injective-digest premises are inhabited only by an unbounded digest (cv `01a11477-0c15`, open; see section 2/4).

**The quote and the refusal share one function, not a theorem.** `resumeQuote` and both `heapUncovered` refusals read `ResumeTail.needed`. No theorem states that they agree; the executed one-cell-short plant rows are the check.

## Row D — Open component contracts


### Asked

The composition contract `C_{A;B}(S,I) = C_A(S,I) ∧ C_B(S, F_A(S,I))`, `F_{A;B} = F_B(S, F_A(S,I))`, as a front-end operation, discharged at `fix`. Per-operation constraints: add needs absence, override needs compatible membership, replace changes type. A front-end commuting square, `template ∘ subst = elaborate(instance)`. `Super` genuinely abstract. Open component artifacts that can be checked separately and are linked before closed Core4, described honestly as staged modularity. Acceptance: a three-package final-self case, where references inside A and B see C's final definitions.

### Decisions and reasons

- **The acceptance case came before the algebra.** It shows the existing semantics already meets the final-self requirement. The algebra is a refactor of where the refusals are decided, and the refusal texts are kept byte-identical, so every pinned cohort row keeps its refusal.
- **A replacement is refused, not admitted.** No source form declares a replacement. Admitting one silently would be a reinterpretation. If we ever want replace, it gets its own syntax.
- **`instance_accepted` was dropped, not proved** (`2ad8c57d`; cv `01a115d6-7ee9`, closed). The obligation was a front-end corollary: a template accepted rigid, plus discharged bounds, implies that the emitted instance checks. Proving it needs the PTy→Ty proposal translation to commute with substitution and canonicalisation. The ruling was to make it protect a real check or delete it, and it protects none. Discharge is decided by name (`checkBounds`), and admission relies on the checker's verdict over the **closed** program, instances included. A translation defect that the theorem would rule out is still caught, as an anonymous `typing refused`. The cost is stated plainly: (a) such a defect surfaces as an unnamed refusal rather than being impossible, and (b) we **cannot** skip re-checking instances. Separately checkable open artifacts therefore remain staged modularity and are not real separate compilation. This is question 5.3 for GPT-6.
- **Staged modularity is named as such** in MODULAR-TYPING §6. Open components are checked once against their bounds, then linked before closed Core4. Nothing below Core4 sees an open term.

- The `super.m` read check inside closed-spec lowering is not routed through the contract module (stated in `1f595131`).

### Asked

### Decisions and reasons

- **Price sizes at a measured worst-case rate under a lowered bound,** rather than pricing time or a superlinear function. The alternatives are recorded in cv `01a11680-f2cc`: a superlinear rate as a function of declared bytes, `decodePolicy` requiring rates ≥ a measured function of `sourceBytes`, or caching the replay per pin.
- **Signature before decision required the signer to sign the outcome it claims** (`Ingress.outcome`). Otherwise there is nothing to verify before deciding. The decision must then reproduce the claim, and a mismatch is a charged `outcomeMoved`.
- **A stale plan is charged.** An honest client whose plan went stale pays for the attempt and re-plans, like reverted gas. Otherwise a stale-plan replay is free work.
- **The charged classes are exhaustive matches with no wildcard,** so each new refusal forces a decision about who pays.
- **Funding is in the gate,** before the run, and is required to cover the envelope plus the deposit. `unfunded_not_gated` makes "nothing runs unfunded" a type fact.

## Row F — Async execution (send, inboxes, answer slots)

Permalink base for this section: `https://github.com/emberian/minidregg/blob/061fcfc1feb476ab5775ad85743e9a3eec0f265a/`, abbreviated **B/** below. Unless marked otherwise, everything here is *read* from source at main `061fcfc1` or from the commit messages in the range.

### Asked

These are GPT-6's row F items:
1. Onward sends from delivered methods go through a bounded, prepaid continuation allowance. The allowance must be conserved across forward, cancel and refund, with bounded fan-out and depth. Until that exists, refuse sends from delivered methods at the interface.
2. Separate STOP-WAITING from CANCEL-IF-QUEUED.
3. Timeouts must not break never-expiring slots.
4. Retries use stable operation ids.
5. Deeper pipelining is allowed only with recorded dependencies: acyclic, a single terminal decision, exactly-once escrow, bounded cascades.
6. FIFO is by entry into the RESOLVED destination queue.

### Built

This landed in five steps, each a flag day in its own commit.

**F1. A send names a deliverable method, decided at the send before any escrow** ([b3c1f575]).
- `Mail.send` (`.object`) first runs `deliverable`. That check loads the target method exactly as its delivery's root frame will: `loadMethod` on the record's `activePin`, applied to the object's view and the arguments. It also checks that the method's Plan type is within `deliveredPlans message`.
- A refused send pushes nothing, opens nothing and credits nothing. The refusals are `notAnObject`, `stateMissing`, `argumentType`, `notCallable`, and the new `notDeliverable` ([B/Kernel/ObjectiveCall.lean#L210](https://github.com/emberian/minidregg/blob/061fcfc1feb476ab5775ad85743e9a3eec0f265a/Kernel/ObjectiveCall.lean#L210)).

**F2. Stop-waiting is not cancel-if-queued** ([c0da309a]).
- A call frame may yield `stop {slot}` or `cancel {slot}` over the reply slot of a message *its object* sent. Both are answered `acked {slot}` at the yield. They are applied when the turn commits, after all its sends (`postControls`, `Mail.control`).
- cancel of a still-queued message:
  - The message is withdrawn (`Inbox.Step.withdraw`); the others keep their order and `head` stays.
  - It is refunded together with every send pipelined on its slot.
  - The slot is decided `cancelled`, or retired if unwatched.
  - A cancel of a decided slot is a no-op that refunds nothing.
- stop of an open slot: the pipelined sends are refunded and the slot is unwatched. The message stays queued and is still delivered, and its delivery retires the slot. A stop of a decided slot retires it at once.
- The new refusals are `notControllable`, `notSender` and `slotInbox`. A pipelined send onto an unwatched slot is refused `notPipelinable` ([L238](https://github.com/emberian/minidregg/blob/061fcfc1feb476ab5775ad85743e9a3eec0f265a/Kernel/ObjectiveCall.lean#L238), [L241](https://github.com/emberian/minidregg/blob/061fcfc1feb476ab5775ad85743e9a3eec0f265a/Kernel/ObjectiveCall.lean#L241), [L255](https://github.com/emberian/minidregg/blob/061fcfc1feb476ab5775ad85743e9a3eec0f265a/Kernel/ObjectiveCall.lean#L255)).

**F3. The bounded prepaid continuation allowance** ([cf471103]).

**F5. Stable operation ids: the invocation nonce IS the operation id** ([57ee7338]; follow-ups [73896c73], and the signature-over-outcome change in row E's [6376fed8]).

The defect:
- `mini activity submit` drew a fresh nonce on every attempt. The nonce is hashed into `invokeTransaction` and from there into every `Inbox.sendId`, so a resubmit after a lost reply was a second invocation and a second message.
- A client that did reuse the nonce got `conflict`, because its retry was re-planned and re-signed, so the bytes differed.

The design adds no field:
- The command nonce is already a signed, per-subject id. `marker` = H(domain, semantics, subject, nonce) is claimed in the spent map, and a spent marker is refused `replayedMarker`.
- Host JSON requires `$.turn.opId` for an invoke, and refuses a top-level `$.nonce` on one by name. `mini` takes the op id from the caller and never mints one.
- `replay` returns `Replayed.exact | Replayed.retry`, each carrying the RECORDED receipt.
- A retry is answered only after `verifyRetry`. That runs admission's own `CredentialSignatureAdmission.verifyNative` under the command subject's current key, over the header the plan showed (`planOutcome`). It uses `retrySnapshot`: the admission snapshot with only the retried operation's own marker counted unconsumed.
- Codec: no change. COMMAND stays v10 and its bytes are identical; only the JSON spelling changed.

The design point on what a retry may differ in:
- The txid binds subject, object, method, args, grants and op id. It leaves out postage, allowance, envelope and account.
- So a retry that changed only those fields gets the original's receipt unchanged.
- The same op id with a different call has a different txid; it reaches the gate and is refused `replayedMarker`.
- There is no content dedupe: a different op id is a new invocation, even with identical content.

### Decisions and reasons

- **The op id is the signed nonce, not a new field.** The nonce was already signed, per subject, and claimed as a nullifier. A second id would be two shapes that agree today. The cost is that clients must mint the id once per operation and keep it across retries; `mini` refuses an invoke without one.
- **Verify before replay.** A retry gets the recorded receipt only after the same signature check admission runs. Otherwise the replay path is an existence oracle: anyone holding the content of another subject's operation could learn whether it landed. S21 and S22 are the executed cases.
- **Postage buys the attempt; allowance buys only the continuation.** A delivery refused at its continuation still pays postage and refunds the whole allowance. This keeps an over-eager onward send from costing the payer more than the attempt.
- **Interface refusal first, then relax.** Step 1 refused every send from a delivered method at the send, with the run-time refusal as backstop. Step 3 relaxed exactly the case covered by an allowance. Throughout, nothing was admitted that would later break for a reason knowable at the send.
- **Authority for controls is the sending OBJECT's frame**, not the invoker. For a decided slot it is the sender named by the decider, after F4 retired inboxes.
- **Cancel of a decided slot is a no-op, not an error.** The converse theorem (`control_cancel_withdraws`) makes the no-op branch mean exactly "the message was not withdrawable".

### G1b. The enforced `law` fragment

**Asked.** Compile a specified source fragment to `Pred`.

**Built**, in three steps.

*Step 1* (`7f10cc0e`): the fragment and its own meaning. [`Compiler/ObjectiveBendLaw.lean#L33–56`](https://github.com/emberian/minidregg/blob/061fcfc1feb476ab5775ad85743e9a3eec0f265a/Compiler/ObjectiveBendLaw.lean#L33):

```lean
inductive LawRef where
  | field (name : String)
  | subject
  | caller
  | height
  | turn

inductive LawExpr where
  | eqC (ref : LawRef) (value : Int)
  | leC (ref : LawRef) (value : Int)
  | inC (ref : LawRef) (values : List Int)
  | eqR (left right : LawRef)
  | leR (left right : LawRef)
  | leROff (left right : LawRef) (offset : Int)
  | monotone (field : String)
  | writeOnce (field : String)
  | not (body : LawExpr)
  | and (left right : LawExpr)
  | or (left right : LawExpr)
  | implies (premise conclusion : LawExpr)
```

`LawExpr.denote` reads the law's meaning off the data directly. It is not defined via `Pred`. [`compile_sound` (`Kernel/ObjectLaw.lean#L507`)](https://github.com/emberian/minidregg/blob/061fcfc1feb476ab5775ad85743e9a3eec0f265a/Kernel/ObjectLaw.lean#L507):

```lean
theorem compile_sound (facts : Facts) (old : Option Data) (new : Data) (before after : State)
    (viewed : views facts old new = some (before, after)) :
    ∀ law : LawExpr, law.fieldsPlain = true → eval (compile law) before after = law.denote facts old new
```

*Step 2* (`6a6cbdda`): parsing and travel.
- A top-level `law NAME: EXPR` parses into the fragment.
- Anything outside the grammar refuses with "law outside the enforced fragment: …". That includes `new.a.b` (edition 1 reads top-level fields only), `old.X` outside `monotone`/`writeOnce`, `>=`, `request.target`, and trailing tokens. There is no fallback to `claim`.
- The source artifact goes to v2 and commits `laws` in its identity. The receiver's replay recomputes them and refuses "offered laws differ from the front end's replay of the package".
- A law in an imported module refuses.

*Step 3* (`66a54085`): enforcement in the kernel.
- OBJECT-RECORD v3: `packageLaws` is set at create and ADOPT from the pinned package cell, never from the request.
- `effectiveLaw = all [pin, packageLaw packageLaws, creator law]`, so a refusal names leaf `[1, i, …]`.
- A law reading a field the declared state type lacks (or one that is not a top-level natural/boolean) refuses `lawField f` at create or ADOPT.

The theorems ([#L576–603](https://github.com/emberian/minidregg/blob/061fcfc1feb476ab5775ad85743e9a3eec0f265a/Kernel/ObjectLaw.lean#L576)):

```lean

    (viewed : views facts old new = some (before, after)) (laws : List (String × LawExpr))
    (holds : eval (packageLaw laws) before after = true) :
    ∀ law ∈ laws, law.2.denote facts old new = true

theorem package_law_enforced (record : ObjectRecord) (facts : Facts) (old : Option Data) (new : Data)
    (admitted : admitWrite record facts old new = .ok ()) :
    ∀ law ∈ record.packageLaws, law.2.denote facts old new = true
```

Measured on the old gate at base 84a6dac8: a theorem's row was its pretty-printed type, so `def Initial … : Prop := True` with every statement text unchanged turned the old gate red on ONE row, the def's. Every theorem reaching it (`check_iff`, `valid_transition`, `cannot_drop`, …) kept a byte-identical row, and `--update` regenerated the whole snapshot.

New shape:
- `Verify/ObjectiveManifest.lean` scans each covered declaration: statement, exact axiom set, the constants of its closure, and the term DAG.
- `scripts/objective-manifest.py` hashes it (SHA-256 Merkle; binder names and metadata excluded):
  - A theorem's `self` hash is its type; proofs are irrelevant, and the axiom column pins what they rest on.
  - A definition's `self` hash includes its body. An inductive's includes its shape and constructors.
  - The `closure` hash is a Merkle hash over the strongly connected components of the constant graph. So it changes when ANY repository definition the statement reaches changes its body, however deep.
- Rows live in per-module TSVs: 585 files at main ([B/scripts/gates/objective-manifest/](https://github.com/emberian/minidregg/tree/061fcfc1feb476ab5775ad85743e9a3eec0f265a/scripts/gates/objective-manifest)).
- The gate is a ratchet. Added rows pass. `removed`, `restated` (statement hash), `redefined` (closure hash moved, statement unchanged) and `axioms` are RED unless `scripts/gates/objective-contract-changes.txt` has a line admitting exactly (name, old contract, new contract, kind) with a commit and a reason. A hand-edited manifest row refuses to load.
- `--draft FROM..TO` (a33b9e10) attributes each change to the commits that touched its cause's module. It narrows to commits whose diff mentions the name. A change no commit explains is written `UNATTRIBUTED:<candidates>` with reason TODO, which the ledger refuses until a person places it.
- **Removal-reason gate** (a7078394, after b23 pinned the removal of `PolicyInstallReceiver.replay_changed_ingress_refused` with no successor). A `removed` line must start with `successor: <Full.Name>…`, `derivable: …` or `obsolete: …`. `successor:` names must be declarations of the fresh run. 9f65b807 lets a private declaration be named by its full name ([B/scripts/objective-manifest.py#L273](https://github.com/emberian/minidregg/blob/061fcfc1feb476ab5775ad85743e9a3eec0f265a/scripts/objective-manifest.py#L273)). **What exactly is caught. This is our answer to "`Safe := True` must be caught".**

Measured, from the 9b90b756 plants and the self-tests that run on every gate invocation:
- **Caught: a changed body of a repository definition that a pinned statement reaches.**

- **Caught: a weakened hypothesis.** Self-test (c), `(_vacuous : False)` added to `admitted_source_semantics`, classifies `restated`, RED.
- **Caught: a proof that starts resting on `sorryAx` or a new axiom** (`axioms` kind), and a removed theorem without a checked successor name.
- **Caught (Lean side, separate mechanism):** an L1 token theorem whose body is a bare field projection (TokenCensus check 3, below).

Read from the design. Each of these is a real gap:
1. **A definition that was `True` from the start is not caught.** The ratchet detects *changes*. An added row passes, so a new theorem over an already-vacuous predicate enters silently. Vacuity of what exists is not this gate's job. The repo tracks it separately (cv 01a105c8-187a, "17 trivially satisfiable structures", open; cv 01a0f802-02f0, hypothesis-ledger rows without a satisfying+refuting pair, open).
2. **The cut.** Constants from Init, Lean, Std, Batteries and Mathlib, plus axioms and opaques, are leaves hashed by kind, name, universe params and type. Their bodies are not followed. Justification given: those are pinned by `lean-toolchain` + `lake-manifest.json` (both in the evidence key), and an opaque's body is invisible to definitional equality.
3. **Admission is by attribution, not by reading.** A legitimate redefinition of a widely reached definition needs one ledger line per affected row. The volumes:
   - Catch-up 33794a1b..e92cbf10: 6,262 lines, attributed by batch with the reason "audited under the old snapshot".
   - Catch-up b10–b13: 7,500 lines (7,224 redefined, 140 root groups).
   - b28 (061fcfc1): 2,512 lines (2,488 redefined, 24 restated, all defs/ctors, no theorem).

   The ledger is 58,142 lines at main. The review that actually happens is over `removed` and `restated` rows, theorems first. `redefined` rows are reviewed by their root (`via`) group, not one by one. GPT-6 should treat "admitted in the ledger" as "attributed to a commit and grouped by cause", not as "a person read this row".
4. **`derivable:` and `obsolete:` are free text.** Only `successor:` is mechanically checked, and only for existence: nothing checks that the successor implies the removed claim.
5. **A HEAD-vs-working-tree defect, found in this range.** 061fcfc1 also committed the manifest pins for `Compiler.DurableIndex`, `Theory.AuthTrie` and `Theory.AuthTrieRange`. ## 1b.1 The Store: from "open the whole image" to "open from the checkpoint, read declared keys"

**Before today.** Every Host request was served from `DurableReceiverIO.Loaded`. That is the full verified materialization: every record decoded, chained, tag-checked and replayed from genesis. Every controller read its journal and consumed set from that snapshot. Two consequences followed. Open cost was linear in history length. And a controller could read "absent" for any key at all, so the code never had to say which keys a decision depended on.

**What landed, in order.**

## 1b.2 Is the light Store a refinement of the full image? What is proven, what is only executed

This is the "maturity" question in section 5 in concrete form.

**Proven (statements quoted, `#assert_axioms` on each):**

- `prepare_agrees` (`PL(Kernel/ResourceTransaction.lean#L1532)`). Two grounds with the same directory, authority, cells and marker answer prepare alike:
  ```lean
  theorem prepare_agrees … (first second : Ground deployment) (command : Command)
      (directory : first.directory = second.directory)
      (authority : first.authority = second.authority)
      (cells : first.cells = second.cells)
      (marker : first.declaresNullifier (…) = second.declaresNullifier (…)) :
      (prepare deployment profile ambient first command).map (fun _ => ()) =
        (prepare deployment profile ambient second command).map (fun _ => ())
  ```
  The revocation, delegation and renounce controllers have their own `prepare_agrees` of the same form. Install has `prepareChecked_agrees`.
- `prepare_light_full` (`#L1557`). A light basis whose served state is `Served.ofLoaded loaded`, with the same directory and authority and with the marker declared, prepares as `Ground.full loaded …` does. The conclusion is the same `.map (fun _ => ())` equation.
- `recordedInvocation_agrees` (`PL(Kernel/DeclaredResourceController.lean#L2405)`):
  ```lean
  theorem recordedInvocation_agrees (domain semantics : Digest) (command : Command)
      (signed : SignedCommand) (first second : Ground deployment)
      (declared : first.declaresTransaction (transactionId domain semantics command) = true)
      (answers : first.recorded (transactionId domain semantics command) =
        second.recorded (transactionId domain semantics command)) :
      recordedInvocation domain semantics command signed first =
        recordedInvocation domain semantics command signed second
  ```
- `receive_executes_as_full` (`PL(Compiler/DurableServed.lean#L822)`). On any full snapshot with the served state's roots, bytes and allowance, which answers the intent's transaction id and nullifiers as the authenticated history does, the executor's observable outcome is the one `receiveServed` acts on:
  ```lean
  DurableView.observe (DurableDataIntent.execute .complete (served.viewAt footprint) intent) =
    DurableView.observe (DurableDataIntent.execute .complete full intent)
  ```
- `validateServed_ofLoaded`, quoted above.

**What these statements do and do not say** [inferred, from reading them]:

- `prepare_agrees` / `prepare_light_full` equate only the *shape* of the outcome: refused with which reason, or prepared. They do not equate the prepared payload. The types differ by their ground index, so the commit-side equality comes from `receive_executes_as_full` on the executor step, not from the controller theorem.
- Each theorem is per step and conditional. Its premises (same directory, authority, cells, answers) are what an end-to-end refinement would have to discharge, and no theorem discharges them for `openHead`.

## 2.3 The storage-deposit quote was not a fixed point

**What was wrong.** An activity record's storage deposit is `storageRate * |encodeRecord record|`. The
record carries digests derived from the transaction id, and those were spelled with `StreamCodec.nat`,
a variable-width base-255 encoding: 32 or 33 octets depending on the value. So the size of a quote,
taken at one nonce and one height, differed from the size of the submission.

Measured: 16 identical quotes gave 8456 twelve times, 8457 three times and 8458 once. About 1 in 4
clients paying their quote were refused `underfunded`.

**How found** (executed). The activity acceptance journey went red at `birth-exact-deposit` with
`underfunded Q Q+1`. It went red again at `a4db78a7` after C3 landed, with quote 8464 against charge
8465. The fix had been written at 02:12 but was **ejected twice** before it landed, on conflicts with
upgrade-turns and with C3. So for about seven hours `main` carried a known defect whose fix was sitting
in the queue.

**The fix.** `92da0719`. The activity record frame goes v5→v6:
- digests in charged records are exactly 32 octets, and heights exactly 8
  (`digest256Stream`, `height64Stream`);
- a value that does not fit is refused by name (`digestWide`, `heightWide`), never truncated;
- `decodeRecord` is strict.

`928a7294` added `resumeQuote` on op 214, computed from the same function the refusal uses. The client's
earlier workaround, probing with a deliberately unadmittable request and parsing the refusal, was
deleted.

The theorems (`encodeRecord_length_mask`, `birth_not_underfunded_at_quote`) are quoted in Row C. The deposit is never the *reason* for a refusal; a refusal from the prefix, because the state moved, keeps its own name.

The defect itself is pinned as a theorem on the old codec,
[`Compiler/Tower256ConcreteBackend.lean#L367`](https://github.com/emberian/minidregg/blob/061fcfc1feb476ab5775ad85743e9a3eec0f265a/Compiler/Tower256ConcreteBackend.lean#L367):
`(StreamCodec.nat.encode (2 ^ 256 - 1)).length ≠ (StreamCodec.nat.encode (2 ^ 240)).length`.

**Flag day.** Any record body in the v5 frame refuses to load. Every world or Store that holds an activity
re-genesises.

**Evidence.**
- **proved**: the theorems above.
- **plant**: a variable-width digest, and separately a variable-width `yieldedAt`, in the record wire.
  Each turns `length_mask`, `deposit_stable` and the refusal theorem red.
- **executed**: `1c9c3e38` ran 50 quote→submit births on the `adbbdfb1` published binaries. 50/50 were
  installed, 0 underfunded, and there was one distinct quote (8501). The activity row ran 309 rows, 0
  failed.
- **Caveat** (read). There was no control run of the 50 rounds against an unfixed Host. Each round also
  learns the deposit from the Host's own `underfunded` refusal, not from the quote op. So the run shows
  that the refusal-derived number is stable. That is the fixed-point property, reached by a different
  route than the client now uses.

**Class: a size that depends on a value, inside a quote → pay loop.** The seat charge looked like the
same class (cv `01a114ca-11a1`). It was closed by reading: no client-declared seat storage quote exists,
so the loop does not arise.

**Open.**
- cv `01a11477-0c15`. `Theory.Digest` is an unbounded `Nat`. Bounding it would falsify the
  injective-digest models: their premise is inhabited only off the deployed hash, and it is
  pigeonhole-false for cSHAKE256. `digestStream` itself was therefore left variable-width. The audit of
  which deployed paths rest on such a premise is open.

## 2.4 The coprocess OOM panic

**What was wrong.** This was landed on 10-01 in `aa5eef8b`, which made native helpers long-lived serve
co-processes. Lean's `IO.Process.spawn` is fork + execvp. When the exec fails, the child prints "could
not execute external process" and calls `exit()`, which flushes the stdio buffers it inherited from the
parent. The child's stdout is the coprocess reply pipe. So a parent with buffered stdout received its own
log lines as a reply.

Measured: `"stor"` was read as the exit code and `"e at hei"` as a u64 length. `readExact` then asked
`handle.read` for that many bytes, and the process aborted with `INTERNAL PANIC: out of memory`, exit 1,
and no message.

**How found** (executed). `scripts/kn2/invoke-undeclared.lean` was red at plain next `fc24cd91`. The
KN2-TRIE worker traced it. The probe had been run without `VERIFIER` set, so the verifier path was
`/nonexistent/verifier`. With the verifier set, the plant passed. The invoke route was not at fault.
The panic was the class: any Host whose verifier or Store path was wrong would crash this way.

**The fix.** `1930a558`. The root added a requirement: fix the cause, not only the parser.
- Helpers start through `/bin/sh -c 'exec "$0" serve' <binary>`. The helper path is a positional
  parameter, never shell text. A failed helper exec is reported by the shell on stderr with status 127,
  and **zero bytes** reach the reply pipe.
- The parent flushes stdout and stderr before the spawn, under the helpers' mutex. This covers the case
  where `/bin/sh` itself cannot run.
- The parser trusts nothing:
  - every reply opens with the 8-byte tag `MDCOPRC1`;
  - each field length is checked against `maxField` = 64 MiB, the Store's `MAX_RECORD_BYTES`;
  - reads are in chunks of at most 64 KiB, so no length that comes off the pipe sizes an allocation.
- Failures are named: `start`, `pipe`, `closed n`, `untagged n`, `oversized field n`, `notUtf8 field`.
- `readReply` is the only reply path:
  [`Compiler/NativeCoprocess.lean#L139`](https://github.com/emberian/minidregg/blob/061fcfc1feb476ab5775ad85743e9a3eec0f265a/Compiler/NativeCoprocess.lean#L139).

**Flag day (helper binaries).** The reply frame gains the tag. A Host refuses a helper built before this
commit (`untagged 8`), and an old Host misreads a new helper. The Host, the verifier and the Store helper
must come from one tip, which the artifact set already guarantees.

**Evidence.** All **executed**. There is no Lean theorem; this is IO code. The rows are in
`scripts/kn2/coprocess-faults.lean`, which is a new merge-gate row, `coprocess-faults`.
- Row 0 is armed against the runtime. The direct spawn of a missing binary **does** leak the parent's 33
  buffered bytes. If the runtime ever changes, this row goes red and says so.
- Row 0b: the launcher alone, with no flush, delivers zero bytes.
- Row 1: a missing helper gives `closed 0`, and `verify` answers `unavailable`.
- Row 2: an untagged reply gives `untagged 8`.
- Row 3: maxField+1 is `oversized`. Exactly maxField followed by EOF is `closed`.
- Control: a 44-byte well-formed reply is answered exactly.
- Against the **old** verifier binary, the Host refused "does not open with the reply tag (8 bytes
  read)". That is the flag-day refusal, observed.
- `invoke-undeclared.lean` with no VERIFIER now requires `unavailable` with zero reply bytes, where it
  used to panic.

**Class: a failure that renders as data.** A failed exec produced bytes that parsed as a reply. This is
the "refusal renders as the expected verdict" family, with a length field that came off the wire.

**Open.** cv `01a117a6-ccc2`. The other `IO.Process.output` sites that parse a child's stdout still get
the parent's flushed buffer back after a failed exec:
- `verifySshsig`, `PortableParticipantPinIO`, `PortableContinuationArchiveIO`, `CarriedSegmentIO`,
  `Host/CarryInspection`, `RetainedArtifactIO` and the GenericSimplex spawn;

## 2.6 The spent set's verifier was not the proved one

**What was wrong.** This landed on 10-06 in `3800b9b2`. `Compiler/DurableSpent` (the spent map and the
transaction index) is what every at-use `byTx` or `spent` read verifies against. It had its own
`verify` and `climb`, and no soundness theorem covered them. `Theory.AuthTrie.verify_sound` existed, but
nothing in `Compiler` or `Kernel` instantiated it at the deployed digest.

Worse, its key paths were
[`keyBits k = bytesBits (digestStream.encode k)`](https://github.com/emberian/minidregg/blob/722c43abf4ea8283431d58c2ed5d409478f140f4/Compiler/DurableSpent.lean#L60),
and `digestStream` has variable length. `verify_sound` requires every key path to have one fixed
length `L`, so its premise could not be met at the deployed shape. "Spent answers are sound up to a node
collision" was therefore unproved for the code that ran. (read: cv `01a11742-712b`.)

**How found.** The KN2-TRIE worker found it while building the keyed index on `Theory.AuthTrie`. It
grepped for any use of AuthTrie in Compiler or Kernel and found none.

**The fix.** `35030f7d`. The spent set and the transaction index become families 0 and 1 of **one**
authenticated trie, with one root (`Head.indexRoot`) and one verifier (`Compiler/DurableIndex`), which is
`AuthTrie.verify` at the deployed digest.
- Keys are 65 bytes: a family byte, a 32-byte primary and a 32-byte secondary. Every key path is 520
  bits (`bitsOf_length`).
- The node digest is cSHAKE256 under `"DREGG/NATIVE-HOST/INDEX-NODE/v1"`.
- `DurableSpent`'s verifier is deleted. Each removed row names its successor.

At [`Compiler/DurableIndex.lean#L131`](https://github.com/emberian/minidregg/blob/061fcfc1feb476ab5775ad85743e9a3eec0f265a/Compiler/DurableIndex.lean#L131)
and [`#L154`](https://github.com/emberian/minidregg/blob/061fcfc1feb476ab5775ad85743e9a3eec0f265a/Compiler/DurableIndex.lean#L154):
```lean
theorem collision_is_cshake (collision : Collision dig) :
    ∃ x y : List UInt8, x ≠ y ∧
      Sp800185Cshake256.hash nodeCustomization x = Sp800185Cshake256.hash nodeCustomization y

theorem lookup_sound (kvs : List (IndexKey × List UInt8)) (wf : WF 520 (entries bitsOf kvs))
    (k : IndexKey) (answer : Option (List UInt8))
    (opening : Theory.AuthTrie.Opening IndexKey (List UInt8) Digest)
    (accepted : Theory.AuthTrie.verify dig bitsOf (rootOf kvs) k answer opening = true) :
    answer = Theory.AuthTrie.lookup (entries bitsOf kvs) k ∨
      ∃ x y : List UInt8, x ≠ y ∧
        Sp800185Cshake256.hash nodeCustomization x = Sp800185Cshake256.hash nodeCustomization y
```
`reveal_sound` (L167) says the same for a prefix reveal: it answers every member under the prefix, none
omitted and none forged, or there is a cSHAKE256 collision.

**The bound, both ways.**
- The floor is cSHAKE256 **collision** resistance at a 256-bit output, which is about **2^128** work. The
  commit message says so explicitly, and says it is "not the 2^256 second-preimage figure".
- An adversary who must hit a *specific* existing root faces the second-preimage problem, at about
  2^256. That is the flattering number. It is not the floor, because the theorem's escape hatch is any
  collision at all.
- Inferred, not proved: key primaries are themselves cSHAKE256 outputs (`primaryOf`, L193).
  `key_injective` is over the 65 key bytes, not over the preimages. So two distinct nullifiers aliasing
  to one key would also take a cSHAKE256 collision, at about 2^128. No theorem states that link.

**Flag day (re-genesis).**
- Tag trailer v4, under the MAC label `…/LOG-TAG/v4`.
- Checkpoint body v4.
- The Store epoch accumulator becomes `"history/mmr-v1;index/trie-v1;checkpoint/v4"`.
- Node space 3 replaces space 2.

What refuses: a Store born with the separate spent map is refused at open, by name
(`seedEpoch_spentMap_refused`, executed in `history-tamper`). A v3 tag never verifies under the v4 label.

**Evidence.**
- **proved**: the theorems above.
- **executed**: `scripts/kn2/index-tamper.lean` refuses each of these:
  - forged membership;
  - forged non-membership: an honest opening with `none`, an empty terminal, an empty root;
  - a family-0 key presented as family 1. That family-1 key is then a verified absence.
  - a deleted leaf at the family reveal;
  - a missing index node, named by `store audit`;
  - a tampered row value, at `Reader.byTx`.
- J0–J8 and JPRIV1 (229 rows) pass with the lane's Host swapped into next's artifacts.

**What is not proved, and is said so.**
- The root that is maintained **incrementally** is not proved equal to the canonical `rootOf`.
  `lookup_sound` is stated against `rootOf kvs`. The bridge from the stored `Head.indexRoot` to
  `rootOf` of the logical map is evidence, not proof:
  - `incremental_matches_canonical` is a `native_decide` over **one** fixed operation sequence
    (inserts, updates, deletes, shared 264-bit prefixes, collapses, delete-to-empty);
  - `store audit` rebuilds every node and compares it.
- Inferred consequence: a bug in incremental maintenance would make reads refuse, or answer against a
  root that is not `rootOf` of the true map. `store audit` would catch it; no theorem would.
- This is cv `01a11741-1af8`, which is open.

**Class: a theory proved beside the code, never instantiated at it.** The soundness theorem was real.
The deployed verifier was a separate function, and the theorem's premise could not even be met at the
deployed key shape. The same shape appears in cv `01a11477-0c15`: injective-digest premises inhabited
only off the deployed hash.

## 3.1 The merge train: next, main, green

**Shape (read: PIPELINE-20261005, queue/README).** One merge keeper agent owns three refs.

- **next** = main plus every queued range, rebased on arrival and published at once. Lanes build on `next`, so a
  conflict shows up when a range is queued, not when it lands.
- **main** fast-forwards to the newest `next` tip whose gate is green *except* for reds recorded as fix-forward
  against a named owner. Those are fixture regeneration, the contract ledger, fixture-dependent rows, or a red the
  owner already has in flight.
- **green** moves only when the gate reports TOTAL red = 0, the contract ledger included. Every green prints an
  evidence key: tree, toolchain, options, dependency closure, gate definitions, fixtures and generated inputs,
  hashed separately. One example, logged at 16:08Z: `key=302d7da5a54f tree=2116e989b0b2 toolchain=391ecbd06896
  options=223e20813dce deps=b5e8a737fbb4 gate=843e3b4e7a1f fixtures=b569fa829e8c generated=60ce6aab9273`.
  Deploy candidates build from green, never from main.

A range arrives as one file, `queue/<lane>.txt`, with fields lane / source / branch / range / what / evidence /
breaks / notes. The lane then sends the keeper a one-line message. The keeper cherry-picks the range into a git-only
pick tree, re-pins generated surfaces, publishes `next`, and gates a batch in a warm gate tree. A range that
conflicts semantically is ejected to its owner with the reason, and the owner rebases onto `next`.

## 3.2 VERIFY-ONCE

**What it is (read: VERIFY-ONCE-20261005.txt, binding since 10-05).** Each fact is established once, by the party
whose job it is.
- A lane builds and checks what it changed: the affected modules, the theorems and journey rows its change exercises,
  and its named acceptance.
- The merge keeper runs the only full post-merge gate, once per batch, on one box.
- Other boxes receive the gated tree's build products by copy ("relay"), never by rebuilding the same tip.
- GitHub CI is an after-the-fact audit.
- The root reads artifacts and does not re-run them.

The earlier packet reported a measured saving of about 58 build-minutes per landing.

contract ledger, the token census, scripts outside every build target. Those reds therefore surface at the keeper,
batched, and are owned by someone else's range. Three examples:
- g1b-law-2 changed `author`'s arity, which broke a `--run` script outside every target (fixed forward by the keeper,
  6e27273e).

  regeneration, four batches later.

The scripts-elab ratchet (3.5) is the structural answer to the second example. The general trade-off stands: VERIFY-ONCE
moves the discovery of cross-cutting breakage from the lane to the gate, so ownership has to be routed afterwards.

## 3.6 Lake-cache poisoning

**What happened (measured on box B; commit 5e20f114).** On 10-07 a per-box shared Lake artifact cache was turned on
(0fc4e15f) to stop lanes recompiling the same modules. Measured: a sibling clone's `lake build Kernel` went from 293 s
(305 modules) to 2 s (307 fetched, 0 compiled).

The native host builder had its own compile loop: `lake env lean SRC -o .olean -i .ilean -c .c` written into
`.lake/build`. Lean learns the module's *package* only from Lake's setup. Without it, Lean emitted
`initialize_<Module>` and `l_Minidregg_*` where Lake emits `initialize_minidregg_<Module>` and `lp_minidregg_*`, and
it wrote a package-less `.olean`. The files sat under Lake's "unchanged" traces, so the next Lake build replayed them
and stored them in the shared cache under the module's input hash. From there every lane fetched them, and no
`lean_exe` linked.

One platform lane's non-umbrella host build (15:56–16:50Z, 733 modules through the bare call), followed by a Lake
build at 16:58Z, wrote 675 cache entries (691 artifacts) with unprefixed names between 16:58 and 17:06Z. The
symptom was an exe-roots red with an undefined `initialize_*` symbol. It could easily have been misread as a code
defect and the range ejected. The kernel deputy recognised it at 17:14Z.

**Fix.**
- The builder now runs `lake build +<Module>:leanArts`, so Lake is the only writer of Lake's outputs.
- A new `lake-cache-audit` marks an entry BAD when its `.c` or compiled `.o` names an in-tree initializer without the
  package prefix or any `l_Minidregg_*`. `--purge` removes it and writes an alert.
- **Guard:** the lake shim runs the audit with `--purge` before every Lake invocation that uses the shared cache. The
  slots watcher runs it every cycle, and the box check fails on a dirty cache, a dirty warm base, or a shim without
  the guard.
- The keeper's per-green check scans the warm base for the unprefixed initializer pattern. The result must be 0, and
  it has been 0 on both bases at every green since.

Collateral: 18 lane trees on box B and 2 gate trees on box A held poisoned local files. They had to be scanned and
cleaned or re-cloned. Two box A trees are marked "POISONED: never build from them".

A second defect sat in the same shim: it forced `LAKE_ARTIFACT_CACHE=true`, and box.env reset `PIPELINE_LAKE_CACHE`.
Every lane that set a "private cache" was silently still on the shared one. The shim now honours an explicit off
switch.

**Class.** This was the third "writer writes through something it does not own" defect of the day:
- 80c104c5: the builder compiled into Lake's own `.c.o.export` objects, so a later `lake build <exe>` linked
  hidden-visibility objects and failed.
- 99ac60f1: cache-restored files are mode-0444 hard links, so Lean opened `.ilean` in place and every consent build
  refused with EACCES. The fix unlinks first and explicitly does *not* chmod, because a chmod would let the write go

- **Row E "whole request".** We could only *price* sizes (source bytes, core bytes, checker fuel), not time. Time per byte is superlinear (measured, Row E4). A linear tariff is therefore honest only below a bound. This is why "the account covers the work" holds only up to 262,144 source bytes, and why one in-tree policy that still declares 4 MiB under-charges about 6× at 2 MB (cv `01a11680-f2cc`, open).
- **Row F "refuse sends from delivered methods at the interface until the allowance exists".** We did this. The backstop run-time refusal still has to exist, because two cases are invisible at the send: a nested call into a sending method, and an upgrade between send and delivery. So "decided at the send" is not the whole story.

# 5. Questions for GPT-6

Each question names the section with the statements.

**5.1 Metering: actual spend under a declared ceiling, or reservation?** (Row C, §2.2)

Today:
- A turn declares a cumulative `extractTicks` allowance, capped by a published per-turn ceiling.
- Each call-tree extraction runs under the per-extraction ceiling, then draws its *actual*, deterministic spend from the allowance. A shortfall is `extractUncovered`, a charged failure.
- The fee is the declared allowance's price, with no refund.
- Single-extraction turns (birth, deliver, exhaust, ADOPT, abortDrained) instead require the full per-extraction ceiling up front, because a budget failure there is committed as a program fault.

Questions:
- (a) Is "declare the ceiling, check at actual spend, charge at declared" the right shape? The alternative is reserving per extraction, which we measured refusing every yielding call tree.
- (b) Should the two shapes be unified? If so, which way?
- (c) Is the one-ceiling overshoot (work done before the draw that refuses) acceptable once it is paid as a charged failure?
- (d) Clients without a prediction declare the whole per-turn ceiling, which our test worlds author as 16× the per-extraction maximum. Is a refund of unused allowance worth what it costs, given that "no fee depends on measured work" is currently a design invariant that makes fees a function of the signed request?

**5.2 `domain_holds_forever` via a turn-end choke point.** (Row A3)

The theorem is proved by cases on `Step` (`turn | inert | foreign`), not on `AdmittedTurn`. The argument:
- every kernel turn's committed intent is the output of `ActivitySeatEnd.finish`;
- `finish` ends with `judgeDomains`;
- `judgeDomains` counts a retired or blanked state as a write;
- it refuses a post that drops a record's domains (`domainsDropped`), and refuses a touched domain cell not indexed by each member's final record (`domainUnindexed`);
- inert seat posts and ordinary-gate intents cannot write the protected cells.

The claim is that no present or future `AdmittedTurn` constructor can escape.

Questions:
- (a) Is this classification argument sound? In particular, is "cannot write the protected cells" for the non-kernel `Step` arms a property we should state as its own theorem rather than leave inside the induction?
- (b) Domain laws are *state* predicates only, judged as `eval law ⟨joint⟩ ⟨joint⟩`. A law that read the height or compared old with new could hold at registration and fail with no turn. The consequences:
  - transition invariants across objects are not expressible as domains;
  - `monotone` and `writeOnce` inside a domain law are vacuous, and nothing refuses them at registration.

  Is that the right line, and should registration refuse those atoms?
- (c) The judgment is priced, but every in-tree tariff sets `domainWork = 0`, and `Tariff.valid` does not require it nonzero. Should validity require it?

**5.3 Dropping `instance_accepted`.** (Row D)

The obligation was: a template accepted rigid, plus discharged bounds, implies the emitted instance checks. We dropped it. Admission's verdict is the checker run over the *closed* program, instances included. A translation defect is still caught, though as an anonymous `typing refused` rather than ruled out.

The cost: we can never skip re-checking instances, so "separately checkable open component artifacts" is staged modularity and not separate compilation.

Questions:
- Is that acceptable at this stage?
- If we later want artifact-level reuse (an open component checked once, linked many times without re-checking), is `instance_accepted` the right theorem? Or is it better to prove that `ATerm.instantiate σ` commutes with the PTy→Ty proposal translation and canonicalisation, and derive acceptance from `Discharges.check_instantiate`?

**5.4 Op-id and replay: does verify-before-replay suffice?** (Row F5)

The design:
- The signed command nonce *is* the operation id.
- `marker = H(domain, semantics, subject, nonce)` is claimed in the spent map.
- `replay` finds the recorded transaction and returns `.retry` with the RECORDED receipt.
- That answer is released only after `verifyRetry`, which runs admission's own signature check under the subject's current key over the header the plan showed, with only this operation's marker counted unconsumed.
- The transaction id binds subject, object, method, args, grants and op id. It excludes postage, allowance, envelope and account.

So:
- a retry that changes only those excluded fields gets the original receipt;
- the same op id with a different call is `replayedMarker`;
- there is no content dedupe.

Questions:
- (a) Does verify-before-replay close the existence oracle you would worry about? What about a retry signed under a key rotated *after* the original landed?
- (b) Should the excluded fields be bound, so that a retry that changed its postage is refused rather than silently answered?
- (c) `retry_unverified_refused` is proved about the pure `retryAnswer`. That the IO receiver routes retries through it is read from the code and checked by a Host plant (S21 red). Is that an acceptable split, or is the routing worth a theorem over `receiveLoaded`?

**5.5 What should "maturity" mean next?** We see three candidate programs and would like your ranking.

- **(a) Refinement proofs of efficient implementations against reference ones.** The concrete case is the light Store against the full image.
  - Timings (Store open, same box, best of 3): 84 ms vs 401 ms at 3000 records, and 60 vs 55 ms at 300.
  - What is proved: per-step agreement given equal reads (`prepare_agrees`, `prepare_light_full`, `recordedInvocation_agrees`, `receive_executes_as_full`). These equate outcome *shape*, not payload.
  - What is not proved: no theorem says the light open equals `Served.ofLoaded` of the full open, and the incremental trie root is not proved equal to the canonical root. Both are checked by execution and by `store audit`.

  Is a whole-open refinement theorem the right next target? Or is "per-step agreement + audit" the right shape for a system that re-executes anyway? The same question applies to the C transcription of the Core4 machine (13–23 ms vs 20–39 s in Lean on one workload).
- **(b) An assurance-case structure.** Our evidence lives in four dimensions, plus gates, ledgers and censuses, but nothing ties claims to evidence in one graph. Is a GSN-style or similar claim/argument/evidence structure worth building over the manifest ledger? What would you put at the top?
- **(c) Lean toolchain upgrade.**
  - Trial v4.30 → v4.34.1 (Mathlib at the matching tag), one cold umbrella build: 28 modules failed, ~1,078 of 1,230 sat unchecked behind them, and 124 checked clean.
  - Three of the failures are kernel deep recursion in `norm_num` primality of 31-bit primes in foundational modules.
  - Our extrapolation of 150–250 failing modules is a guess.
  - The motivation is kernel-soundness fixes in 4.33/4.34.

  Upgrade now, as a dedicated campaign, or after the module-system work?

**5.6 Charged failure: is charging a stale plan right?** (Row E3)

The signer signs the outcome it claims, and the decision must reproduce it. If state moved between plan and submit, `outcomeMoved` is *charged*, like reverted gas. Malformed, ungated or badly signed requests cost nothing, and funding is checked in the gate before anything runs. An honest client racing a busy object pays for each lost race. Is that the right incentive, or should a moved outcome be a cheap rejection when the moved cells are disjoint from the claim's reads?

**5.7 Thin consent signs a delegation's parent by id, not the authority root.** (§1b.4)

The argument that this is not a weakening:
- the executor reads the parent at the signed id from the real pre-state;
- every other thing the root pinned is a gate that can only refuse;
- the root added contention, not binding.

Do you agree? Is there a delegation attack that the whole-root pin prevented and the id does not?

**5.8 Pricing superlinear front-end work.** (Row E4)

We price at the worst per-byte cost up to a lowered bound. The alternatives we recorded:
- a superlinear rate as a function of declared bytes;
- `decodePolicy` requiring rates ≥ a measured function of `sourceBytes`;
- caching the replay per pin. The ruling for method loads is a per-turn cache with a theorem that cached = uncached.

Which would you choose for a system whose admission is re-execution?

**5.9 Ledger granularity for `redefined`.** (Row H3, §3.4)

A legitimate change to a widely reached definition produces one ledger line per affected row: 2,488 at b28, and 7,224 in one catch-up. Admission is by commit attribution, grouped by root, not by reading each row. Should a root-level admission cover dependents whose *statement* hash is unchanged? Or does that reopen the `Safe := True` hole, since a vacuous redefinition changes no statement either?

**5.10 Vacuity of what already exists.** (Row H3 gap 1)

The manifest gate catches *changes*. A definition that was `True` from the start, and new theorems over it, pass. We track that separately with a hypothesis ledger that requires a satisfying and a refuting witness per hypothesis family. Is there a cheaper mechanical check you would trust, for example over theorem premises: flag any premise whose type is inhabited by a closed term found by `decide` or `exact?`?

**5.11 Files written through hard links.** (§3.6, §3.7)

**5.12 Is our proof base shaped right: invariants, per-step facts, instances, and the missing temporal layer?**

Ember asks whether too many of our theorems are about fixed applications to near-constant parameters, rather than about whole trees or traces of possible computations. The root's impression from today sorts them into four layers. The measured census follows the list:
- **Invariants over every reachable world.** `domain_holds_forever`, the checkpoint and upgrade invariants, and `escrow_conservation` over the ledger. These are inductive safety properties over all traces.
- **Per-function universals.** Most of today's theorems (`failed_charges_and_rolls_back`, `invocation_delegated_authority`, `compile_sound`). They hold for all inputs, but say nothing about sequences.
- **Closed instances.** `native_decide` checks of specific encodings, fixture projections, and the three C4 fuel instances (§4.3). Journeys, though named as rows, are executions on chosen inputs and not proofs.
- **Liveness and progress: largely absent.** "Every send is eventually delivered or refunded", "a drain eventually completes", "an activity reaches a visible step or diverges silently, never stuck in between". `migrate_cannot_fail` is a no-stuck property, and Row B's reference is a step correspondence, not a coinductive bisimulation over infinite interaction trees.

**Measured after this was drafted.** The census ran over the elaborated environment at `cfdaf64d`. It covered 23,006 user theorems in Theory, Kernel, Pred, Effects, Compiler, Selvage, Assurance and Host. The classifier works syntactically on each statement. - **Liveness.** None of the 42 "temporal" theorems is liveness over infinite executions. They are bounded halting on the demand machine and fuel-completeness of two evaluators. About 12 merely project assumed-liveness structures.
- **Where the reachability invariants live.** Only Theory (138), Kernel (158) and Assurance (39) have any. Compiler and Selvage have none.

- **(b)** For Row B, is a coinductive bisimulation (interaction trees, `paco`-style, or a guarded fixed point) worth the machinery in Lean 4? Or does a step correspondence plus a separate divergence/termination classification capture what matters?

# 5b. Your earlier assessment of Objective Bend (at 84a6dac8): what changed, what is still open

Before the rows, Ember asked for your view of Objective Bend as a language. Your answer: build it as a language for persistent, governed computational objects, keep the law idea, make upstream Bend 2 compatibility an explicit engineering target, and put the proof boundary as a total logic about partial programs. Here is where each point stands at main `061fcfc1`. Status is from a grep of `docs/` and the code (measured) unless marked.

**Done since you wrote it.**
- **"The current Objective `law` is unchecked metadata."** It isn't any more (Row G):
  - `law` now means an enforced predicate: a source fragment compiled to `Pred` with `compile_sound`, carried in the artifact, and judged on every write;
  - the old unchecked meaning is renamed `claim`;
  - registered invariant domains add a law across several objects, judged at turn end (Row A3).
- **"Governing restrictions must not disappear when a later component overrides a method."** Laws compose by conjunction (unchanged). Row D also refuses a type-changing replacement (`replace-undeclared`) and makes `Super` rigid, so an override cannot quietly reinterpret what it overrides.

**A new hazard that this change creates, which we want your view on.** Objective's `law` now means a *runtime-enforced transition predicate over state*. Upstream's `law` means a *statically proved proposition about a program*. They share a word but are different kinds of guarantee:
- An upstream `LAWS.bend` brought into Objective Bend cannot become an enforced `law`, because most such laws are not state predicates.
- An upstream law cannot become a `claim` either, which would silently drop "must be proved".

We think it needs a third construct: a *proved* obligation, with a proof status attached to the exact proposition, implementation, semantics and dependency closure (your phrase). It has to be distinct from both `law` and `claim`. Nothing like it exists yet. Should the three be separate keywords, or one construct with an explicit status?

**Still open, none started (measured: `docs/OBJECTIVE-BEND.md` doesn't mention upstream compatibility, sealing or policy diffs).**
- **Sealed imports vs open extension points.** You noted that late binding to the final whole can invalidate an imported proof of `∀x. P(f x)` once a helper `f` calls is rebound.
  - Today, Row D's composition contracts govern what a layer may override, and admission re-checks the whole closed program.
  - But re-checking the program is not re-checking imported *theorems*, and we have no construct that seals a module over its original dependencies.
  - We agree this should be two constructs. Dropping `instance_accepted` (§5.3) makes it more pressing, not less.
- **A compatibility suite against upstream Bend 2.** Classify each program as accepted unchanged, accepted with a documented adaptation, intentionally unsupported, or mistranslated. Nothing exists yet.
  - The corpus could start from the historical `.bend` originals removed from the tree on 10-04, which are in git history.
- **Policy-change review using the decision procedure.** `UNSAT(L_new ∧ ¬L_old)` over a constrained state/request domain, with a concrete counterexample when a change weakens a law, and `SAT(L_1 ∧ L_2)` for conflicts with inherited restrictions. `Pred/Satisfiable*.lean` already return checked witnesses and certificates, so this is mostly a front-end and domain-constraint question.
  - Of everything in your note, this looks like the cheapest step towards making laws useful to authors.
  - It is subject to the DNF cap and to the `hashEq`/`ran`/`witnessed` exclusions you named.
- **The total logic about partial programs.** Our invariant theorems already have your shape: `I(s) ∧ Step(s,a,s') ⇒ I(s')` plus an initial state, over `Reachable` (`domain_holds_forever`, the checkpoint and upgrade invariants). But no *author-facing* proof language exists, so no Objective Bend program can state and discharge its own invariant. Partial programs are still not allowed to count as proofs: there is no route by which they could.
- **"A few demanding applications that reuse one another's components."** This is your measure of success, and we haven't built towards it deliberately. Today's journeys exercise the kernel through small driver programs (Tally, a bank domain, seats, bounty, send/call chains). None is an application that reuses another application's components. Row D's three-package acceptance is the closest thing.

**Our question back.** If we picked ONE of these for the next wave, ranked by how much it would show whether the language is worth its ecosystem cost, which would you choose? Our guess: the policy-diff tool plus one real two-application reuse case, with sealed imports designed (not built) alongside.
