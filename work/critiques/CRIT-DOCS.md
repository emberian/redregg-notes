The specification is not yet a substitute for reading the Lean. Its core typing rules largely restate the source exactly. Its account of contextual execution omits conditions that change observable behavior. Its soundness appendix lists results without supplying the dynamic typing needed to state them precisely. The README advertises the contextual behavior more strongly than the implementation supports.

The first fetched origin/main was 992ec0555723c004b291b709bd02054e67227b74. The source review continued through 1a32753585492daa73dfb39f1d5deb9ee12f9e34. After the README's first screen, this reader believes Objective Bend is a monomorphic functional language embedded in a persistent object system. They believe methods compute transitions and laws constrain those transitions. They believe an immutable package can contain alternative implementations selected against authenticated observations. Those beliefs describe the tree. They also read that every member re-executes every step before accepting a World. That statement excludes the thin-adoption path described later. The opening needs to say that replay starts from genesis or a trusted base. The phrase “shared state with one writer” does not tell the reader whether followers can be kept on different lawful histories. Protocol §6.1 answers that question much later. State the absence of agreement among followers beside the single-writer model.

“The language is small and exact” is the first sentence I would strike while reading. Smallness requires a stated boundary. The eighteen constructors exclude the loader, contextual preparation, extraction, laws, guards, relation reads, call derivation and settlement. Exactness is the obligation of the document that follows. Neither adjective helps me identify the computational model.

The sentence that would make me stop and check the source is “Two properties set Objective Bend apart from other ledger languages.” The first property invokes contextual modal type theory. The second includes ordinary generation of bytes for later validation. The comparison class is unspecified. The claim makes novelty carry the introduction before the document establishes the mechanism. Replace it with a description of what selection checks and what package generation returns. The later literature section already provides a better basis for comparison.

The first screen also conflates the scope of a theorem with the scope of a product claim. checked_never_stuck concerns a checked closed term and a checked library. It does not establish that package loading, hole preparation or result extraction succeeds. A source-level safety claim is appropriate here. The path from an installed package to the theorem's premises needs to be explicit.

The counter example can be followed after reading the explanation below it. It cannot be copied as the complete core-text package it is called. S, Req, Verdict, Row, Choice, Edit, Call and Opt are editorial abbreviations. PRE, POST and G are substitutions performed outside the displayed text. The page discloses the abbreviations. It still needs a link to a literal runnable package and an exact recipe for supplying G. Lang/Journey/Readme.lean provides a Lean string, not a standalone authoring artifact. Its RM2 path calls Surface.readPackage. The README and conventions should identify the actual parser used by their executable evidence.

The interface is the largest initial obstacle. It introduces four curried signatures before giving one invocation. Put the method shape immediately before the interface. Explain that c0 and e0 are optional slots rather than lists. Explain that an empty calls record is a type-level prohibition on calls. Explain that the law's refused injection is a language value until the kernel interprets it. These distinctions carry more information than another sentence asserting that the language is exact.

The relation declaration raises a question that the text does not answer locally. Why must choosing a candidate pin an absent row? Upsert replaces the observed row state, including an observed absence. That observation belongs to the signed call. The example should show the row pin in the first choose operation. It should also say that candidate indices start at zero. “Candidate 1” means the candidate whose body is 10. “Candidate 0” means the candidate whose body is 1.

The law introduces an unrelated complication. It contains write and relaw arms that the counter itself cannot reach through those receivers. The explanation eventually says that those arms matter when the package is an extra law on a data object. The example never uses that role. This makes the reader audit dead cases before understanding the main execution. Keep the exhaustive occasion type in the specification. Explain the counter's reachable occasions next to the example's law.

The contextual dependency is observable. Revoking G prevents a later bump from adding ten. The same installed package can then add one after a new selection. The hole is not merely a comment. The example nevertheless demonstrates a revocable switch between constants. Its context is empty. Its hypotheses are empty. Its guard is true. The candidate does not consume a value supplied through contextual substitution. It does not exercise strengthening. It does not explain why that grant is a justification for adding ten. The source makes G a grant from B to A over a separate data object. B's authority to bump the counter does not depend on exercising that grant. State that G is a deliberately chosen liveness dependency, not the counter's authorization check.

The most informative step is currently underexplained. RM10 runs choose after G has died. choose belongs to the same package as bump. Preparation therefore encounters the blocked bump hole while loading choose. choose succeeds because its computation does not demand that field. Put this fact beside the repair step. Show the prepared bump field becoming a refusal while choose remains executable. Then add one small example with a nonempty context and a used hypothesis. That example would distinguish contextual substitution from a table lookup.

The journey establishes less than a continuous transcript suggests. RM4, RM7, RM9, RM13 and RM14 discard the Run returned by go. They retain the verdict text for their assertion. These are probes against selected states. They are not all retained transitions in one evolving log. The RM9 count check reads the retained pre-probe World. It does not independently establish rollback by inspecting the returned post-probe World. Describe the example as a scenario with refusal probes. Do not present those checks as evidence that every displayed attempt has been incorporated into one follower history.

spawn interrupts the contextual example to teach package-tree encoding. The reader must trust two opaque hex fragments to understand an unrelated feature. The generated package exports a constant and has no method. It does not demonstrate a protocol or an object lifecycle. Move this material to the binary chapter's worked examples. The opening example should demonstrate selection, invalidation, refusal and repair without changing subjects.

The WebAssembly comparison is a demand for semantic completeness, not chapter naming. I consulted the official WebAssembly core introduction, validation conventions, execution conventions and type-soundness appendix. WebAssembly explicitly supplies equivalent prose and formal rules. It defines runtime typing before stating soundness. Objective Bend adopts the chapter arrangement but does not maintain that equivalence across its runtime. The relevant comparison is [WebAssembly validation conventions](https://webassembly.github.io/spec/core/valid/conventions.html), [execution conventions](https://webassembly.github.io/spec/core/exec/conventions.html), and [type soundness](https://webassembly.github.io/spec/core/appendix/properties.html).

Chapter 0 promises a rule followed by prose that says the same thing. Chapter 3 mostly fulfills that promise for terms. Chapter 4 stops doing so for package execution. Method setup, extraction, loading, selection and repair become numbered descriptions of functions. Function names are useful citations. They are not definitions of the omitted operations.

There is no missing core term former in the typing or CEK sections. All eighteen term formers have typing rules. E-Lit explicitly covers the four literal constructors. E-Hole states the behavior of a residual hole. The missing formal rules lie at the boundaries the specification also claims to define. Extraction has no judgement with an input budget and an output budget. Capture-avoiding filling has no equations. Strengthening has no definition of variable occurrence or index erasure. Repair has no World transition tying a permitted selection-row update to the next invocation. The clauses for method shape use rowsOf and callSlotsOf without defining their recognition algorithms completely.

The generic citation at the start of §4.2 covers the machine rules. It would be wrong to report those rules as wholly uncited. The failure is navigability. An entry such as “E-Var … E-Hole” points to a whole block and one large definition. The index does not provide a separate target for each rule. §3.1's well-formedness rules have no individual names. Several tables cite unqualified helper names whose module must be recovered from earlier prose. Give each rule a stable anchor. Give each cited declaration a link to the reviewed revision. This reader needs to move from a premise to its definition without searching the repository.

The conventions also need a separation between notation and semantic helpers. In the support rules, package(c) and lawslots(c) are not defined in chapter 0. Their ordinary meanings overstate the tests actually performed. In the theorem prose, “holds of,” “meaning,” “final,” and “chain” require relations. BigStep is named but never specified. Outcome.Final is not defined in the document. The implementation defines it as every outcome except a ticks fault. A stack fault is final in that sense.

“Refusal” has incompatible uses. Chapter 0 says a refusal is never a language value and never a verdict. The language defines Verdict as a sum containing refused bytes. The kernel defines Verdict.refused. Chapter 4 then uses refusal for a typed term, a machine fault, a law result and a kernel rejection. Distinguish these four objects before using the same word for them. “Row” also means both a labelled syntax list and a persistent relation entry. Both meanings are defined, but the document needs qualified terms when they meet in contextual preparation.

One false definition is immediately actionable. §2.6 says retract false makes a relation insert-only. Lang/Package.lean relEditTy always includes upsert. Lang/Rel.lean editOf accepts it independently of retract. The README's choice relation relies on this behavior. The flag forbids retraction. It does not forbid replacement.

The displayed premise leaves that grouping to spacing. G-Case, G-Inj and G-Refuse match the implementation. guardedBy_sound is a faithful informal summary of GuardedOk. The operational audit matches E-Var, E-Lam, E-App, E-Fix, E-Record, E-Ref and E-Hole to Lang/Eval.lean step. R-AppR matches closure application in the captured environment. R-GetKnot matches the retained get frame and self binding. R-ExtendKnot matches the retained extend frame and the knot's original environment. The machine-state grammar suppresses an implementation invariant. Lean stores a depth counter separately from its stack. The specification says it is carried with the state but then writes the cap check against the stack length. This is a legitimate abstraction for reachable states. Cite step_depth and define the initial equality. The unrestricted Lean State type also admits states where the two differ.

The tick explanation contains a false inference. walked_le bounds accumulated primitive-byte work over a run started at State.init. It does not bound the work performed by each transition. R-PrimPay spends ticks before R-PrimOk performs the byte operation. A 65536-byte concatenation performs its byte work on the final primitive transition after paying 2048 primitive ticks. Thus “So one tick does at most a bounded amount of byte work” cannot mean the preceding bound of 32 bytes applies to each transition. Say that the charge is amortized over the run. Distinguish the 2048 primitive ticks from the additional evaluation and halting transitions.

The payload-writer cost description also exceeds the executable definition. primBytes for u64be, sized and dsized constructs the would-be result before written inspects its size. primEval constructs that result before appended checks its size. The prose says an oversized payload writer walks nothing and pays before walking any byte. The Lean definition does not establish that implementation property. A source-level accounting measure is not a proof of allocation or copying behavior in compiled code. State what walked counts. Do not turn it into a latency or allocation guarantee.

Preparation is charged after setup has loaded and instantiated the closure. runMeasuredWith obtains S before testing S.preparation against budget. The charge is a conservative formula over committed candidate sizes. It is not a count of the operations already performed by loading, checking, support traversal and filling. Laws and relation guards each receive lawTicks separately. Their ticks do not enter the method tree's tick pool. A reader designing an attacker model needs these distinctions beside the resource claim, not scattered across §4.6 and §4.8.

The source has enough machinery for a soundness exposition. Lang/Proofs/RunTy.lean defines ValTy, EnvTy, ThunksTy, StackTy, StateTy and LibTy. None is stated in the specification. Lang/Proofs/Sound.lean step_sound combines preservation and progress. run_sound lifts it by induction on fuel. checked_never_stuck then uses checkLib_sound and check_iff. Write those premises and conclusions. Explain the closure case, the knot case and suspended-field typing. Add the separate extraction argument. That would let this reader re-prove the intended result rather than invent the missing invariant.

checked_never_stuck's summary in §4.4.3 is faithful for the empty hole signature and a checked library. run_agree's summary needs the same library and stack cap in both runs. run_bigStep and run_fault_bigStep have the stated exception for stuck, ticks and stack. bigStep_run quantifies over a sufficiently large stack cap as well as fuel. It does not say that every reference value can be reached under the deployed cap of 4096. Preserve that limitation when explaining completeness.

The contextual section is the weakest semantic boundary. Sup-Row and Sup-Cell match supportLive when their notation means authenticated point lookup and successful digest decoding. Sup-Law tests for matching bytes in slots 2 through 15. Sup-Package tests slot 0 for matching bytes. Neither cellGoverned nor cellRuns checks the cell kind. The theorem selectHole_contract_support states these slot predicates exactly. The prose says the cell is governed by a law or runs a package. A grant also has slot 0, where it stores its target. A matching slot in a grant can satisfy cellRuns without the grant being an object that runs code. Define the actual structural predicates. selectHole's nine-step description largely matches the implementation's order. It distinguishes missing observation from a failed observed support. It stops at the first failed category. It collects every failure only within the three candidate-support filters. Hypotheses are checked by a sequential fold that returns its first failure. That order is observable through refusal text. A model checker needs an ordered selection judgement with explicit error propagation, not an unordered set of success premises.

selectHole_origin states the selected index, selection-row version, original candidate and live supports. The document summarizes that result accurately. selectHole_hypotheses is conditional on successful selection and on an indexed support hypothesis. The summary should retain both restrictions. selectHole_factor also assumes h.check Δ succeeds. Selection alone does not establish that the factor is typed. selectHole_live_selects requires every guard pin to be observed in addition to the guard evaluating to true. The prose theorem omits that premise. A guard that ignores its boolean argument can return true with an unobserved pin, while runHoleGuard refuses before evaluating it.

Res-Sel and Res-Block match resolveHole and HoleResolution.body. blocked_step proves that the blocked term faults in one transition. It does not prove that a prepared package containing that term reaches evaluation. instantiateHoles_typed is conditional on successful preparation. These two conditional results do not compose into the README's unconditional claim that a failed support produces a typed refusal which fires only on demand.

There is a concrete counterexample to that demand-only description. Give one candidate four cell supports with valid 32-byte digest encodings. Pin a selection row naming that candidate. Omit all four support cells from the caller's view. selectHole returns unpinned with all four coordinates. HoleRefusal.wire renders “holeUnpinned” followed by four cell:HEX coordinates. The resulting ASCII reason is 292 bytes. Bounds.reasonMax is 256. HoleResolution.body embeds the reason unchanged in refuse. inferE rejects that refuse with badReason. instantiateHoles converts the failure to holeInstanceType.

Put the hole in a suspended field that the invoked method never selects. The prepared-body checker still visits that field. Loading fails before the CEK machine can decide what is demanded. The package can pass installation because unresolvedBody substitutes the short reason holeUnresolved there. HoleROM.check imposes no support-count limit that excludes four supports. HoleWire accepts that support list. This counterexample follows directly from the inspected definitions. It needs a focused regression in the implementation lane. The document must acknowledge preparation failure separately from demand-triggered refusal. Removing the reason-length check would not be a documentation repair.

There are additional preparation failures even with short refusal names. fillBounded rejects excessive estimated work or expanded size before execution. The unconditional demand-only sentence therefore needs a successful-preparation premise independently of the long-reason defect. A metatheory section should distinguish a blocked resolution, an admissible filled term and an invoked computation. The current prose moves between them without naming the intermediate obligations.

Repair is stated as a description of a client action. No rule links a successful choose call to a new selection row and then to a successful future demand. No rule gives repair authority or a progress condition. The document correctly disclaims automatic fallback. It must also distinguish possible repair from guaranteed repair. The object's methods and laws can make every alternative unreachable.

The repair paragraph contains two direct citation defects. stale_behind_forever is a theorem about stale pins with a collision disjunct. For programmed objects, the package is immutable. cellLaw and cellPackage need separate persistence explanations.

The paragraph I would put first in the README is:

nanodregg is a single-writer object system whose programs are written in Objective Bend. An immutable package defines typed state, methods that propose atomic changes, and laws that judge those changes. Contextual holes select code committed in the package against a caller's authenticated observations of the World. Members check the writer's log by re-executing it from genesis or a trusted base. Lean defines the language and transition rules. The deployed writer and followers execute compiled Lean. The system studies checked execution under changing observations without providing consensus among followers or secrecy from the operator.
