CollectiveAdoption reuses the existing Workshop CatalogReview Candidate,
Recommendation, Decision and Adoption. Proposal commits the round, exact
base/candidate source+program+revision, base/candidate prototype IDs, kind root,
instance root, migration digest, policy, electorate and quorum. Cast checks
round, eligibility, unique ballot use, valid unique electorate and state,
positive attainable quorum, and open phase. Tally is derived from retained
ballots; there is no independently trusted tally input. General cast_exact
proves the whole expected predecessor, one-ballot successor and derived counts.
Resolution closes the exact ballot image. prepare_install derives endorsement
from that retained closed valid image and checks current base/prototype/root/
migration. Domain endorsement is not an installation capability.

SingleSellerAllocation is the existing single-seller mechanism: decreasing bid
price, original admitted-book index ties, capacity prefix, last filled price.
General allocation_conserves proves filled quantities plus remainder equals
the original supply for every source input. It does not assert full fairness
or compiled-machine arithmetic refinement.

UniformProRata is separately named: the DrEX two-sided uniform mechanism,
lowest grid index maximizing volume, exact integer floors/largest remainders,
original admitted-book index remainder ties. There is no float tolerance or
worker-selected book/grid/order. Its algorithm and no-empty-grid law pass the
actual Book checker; general conservation/capacity/optimality proofs remain
to be joined, and no native DrEX monetary receipt is claimed.

SingleSellerSettlement supplies a source-owned logical balance model, exact
sampled resource/root/field/preimage write binding, complete account alias and
principal/asset/reservation validation, and per-recipient result data. Its raw
BalanceWrite is NOT a native monetary settlement: native accountBalance raw
writes are forbidden. This useful receiving mismatch was caught before landing.

CanonicalBookSettlement is the actual monetary construction direction. It
derives only CanonicalResourceKernel.Operation.transfer-shaped intents over ONE
canonical book ID/root. Every Account{account,asset,balance} input must be read
from that same native book and have actual book.accounts membership. Negative
balances refuse this natural-number domain profile. Canonical native
Batch.Admission applies each operation to the preceding resulting book.
Coordinate identity is (account,asset), so one account may own both money and
goods; duplicate reservation coordinates are rejected. Unspent funds remain
reserved; no refund transfer is invented. PrivateResult is typed intended-
recipient data, not a cryptographic privacy certificate.

CanonicalUniformSettlement consumes the distinct UniformProRata source through
the SAME Transfer ABI. It collects admitted bid currency and ask goods into two
clearing pools, then distributes the corresponding goods/currency. It checks
per-side units equal the computed volume, per-order quantities/limits/backing,
assets and coordinate distinctness. Both pools should finish unchanged. Its
result explicitly retains Bid/Ask and the intended audience. No second native
money primitive or host-selected allocation is introduced.

Funding order is explicit: native_performance_construction and world language
are defining one prepared financial token that applies the validated funding
burn first, then application operations. Domain Account balances must come from
that explicitly derived settlement-prebook, with provenance from the original
durable book root plus the validated funding transition. Feeding original gross
balances while charging later would be a wrong sample. The source only preserves
the supplied original expectedRoot; native input binding must prove this bridge.
